## Problem (verified 2026-10-10)

`--loop` was built so that a model other than the builder reviews the builder's work. Its fixer, however, is a second headless CLI chosen by the review tool, never the context that built the code:

1. `detectFixer` (src/loop.js L224) takes `--loop-fixer`, else the first of `codex`, `claude`, `agy` on PATH. It consults neither the reviewer that was just resolved nor the builder environment (`builderContextKey`, src/llm.js L1221).
2. Inside Claude Code with no Gemini or OpenAI key, the reviewer ladder (src/llm.js L1378) selects the `codex` CLI and the fixer ladder selects `codex`: one model reviews, fixes from a bare prompt, and re-reviews its own fix. With only Anthropic reachable the same collapse happens on `claude`.
3. `buildFixPrompt` (src/loop.js L464) hands the fixer the finding text and a file list only. The spec, ticket and conversation that produced the code never reach it, and it cannot decline a finding: `buildLoopSummary` hard-codes `acceptedCount: 0`.
4. The only same-provider check in the loop (`--loop-unsafe-allow-fix-secrets`, L955-982) REQUIRES fixer == reviewer. Nothing checks that they differ.
5. `skills/adversarial-review/SKILL.md` "Output discipline" says findings are returned verbatim and "the human (or the next agent) decides what to fix", which is the builder-fixes model, while the same file advertises `--loop`.
6. 3.0.0 R1 (ROADMAP.md L197-209; tickets T86, T97) adds the fixer family to the builder set B, so a compliant `--loop` from a Claude Code session with a codex fixer needs a THIRD family to review. Builder-fixes needs two, and the one with the intent does the fixing.

## The protocol (binding content of SKILL.md)

The SKILL.md is the deliverable; this section is its normative content. Wording may differ, rules may not.

### Frontmatter
`name: adversarial-review-loop`; `user-invocable: true`; `license: Apache-2.0`; `argument-hint: "[--max-rounds <n>] [--test <cmd>] [--base <ref>] [--scope working-tree|branch] [--provider <p>] [--providers ...] [--verify] [focus...]"`; `metadata.version` equals package.json's version at release. The description names the trigger phrases: "arl", "review and fix until clean", "converge the review", "fix the review findings", "loop the adversarial review", "iterate until the review passes", and states the division of labour in one sentence: an independent model reviews, this context fixes.

### Arguments
- Skill-owned: `--max-rounds <n>` (ceiling per block, default 20), `--max-time <duration>` (wall-clock checkpoint per block, default `2h`, D23), `--test <cmd>` (validation command; overrides discovery).
- Everything else passes through to `npx adversarial-review` unchanged, including `--base`, `--scope`, `--provider`, `--providers`, `--quorum`, `--verify`, `--passes`, `--fail-on`, `--min-confidence`, `--include-files`, `--findings-ledger`, and free focus text.
- Refused with a one-line explanation, no review call made: any `--loop*` flag (that is the other mode), `--input` (no working tree to fix), `--prompt-only`, `--json` (the skill adds it itself).

### Preconditions (checked before the first review)
1. Inside a git repository (`git rev-parse --show-toplevel`).
2. Branch mode (`--base` given, or `--scope branch`): the working tree must be clean (`git status --porcelain` empty) and HEAD must not be detached. Otherwise stop with exitReason `precondition` and say which. Rationale: branch-scope review diffs `merge-base...HEAD` (src/git-context.js L194), so uncommitted edits are invisible to the reviewer; per-round commits are what make fixes reviewable, and a clean start is what makes `git add -A` safe.
3. Working-tree mode: no git precondition.
4. Validation command resolved (section "Validation") or recorded as absent. The resolved command is printed before the first run (D28). It executes with the session's privileges, exactly as running the tests by hand; arl is for checkouts the user already trusts to build.
5. Independence (section "Independence") is evaluated on the first review's stderr, not before it, because the CLI resolves the reviewer at run time.

### Round structure
Round r (r ≥ 1): one review call, then (if flagged) one fix step, then validation. The gating set G_r is the findings of round r that gate (section "Gating set"). Fix rounds F = number of fix steps performed. The ceiling applies to F.

Review call: `npx adversarial-review --json <pass-through> [focus]`, stdout and stderr captured to separate files, never merged (D26): `> <scratchpad>/arl/<run-id>/round-<r>.stdout.json 2> <scratchpad>/arl/<run-id>/round-<r>.stderr.txt`. A merged stream puts log lines inside the JSON document and fails every round. Exit codes: `0` approve, `2` needs-attention, `1` error. On `1` the run ends with exitReason `review-error` and the stderr tail verbatim; nothing is retried automatically.

### Independence
From the first review's stderr read the reviewer identity line (src/llm.js L1607-1609): `Using local CLI agent: <cmd>` or `Using LLM provider: <provider> (model: <m>)`. Map to a family: `codex`→openai, `claude`→anthropic, `agy`→gemini, `agent`/`cursor-agent`→cursor, `copilot`→unknown, `opencode`→unknown; API providers `anthropic`/`openai`/`gemini` map to themselves; `vercel`/`gateway` → the family of the model id if it is recognisable, else unknown. The builder family is the harness the skill runs in: Claude Code→anthropic, Cursor→cursor, Antigravity→gemini, Codex CLI→openai, Copilot→unknown.

Stop with exitReason `no-independent-reviewer` before any fix when ANY of: the stderr contains a "fell back to" warning (L1389, L1394, L1422, L1447, L1452); reviewer family equals builder family; either family is unknown; no identity line is found at all (D25: absent is unknown, never a pass). The stop message names what would unblock (an API key or CLI for another family) and says that passing `--provider <p>` explicitly overrides. After 3.0.0 D1 lands, `meta.independent` in the JSON document replaces the stderr parse (`true` → proceed, anything else → stop).

Override: an explicit `--provider` in the invocation skips this check (the CLI's own 3.0.0 R1 enforcement still applies). The summary then carries `independence: "overridden"` and its verdict is never `approve` (D24): exitReason keeps its value and verdict is `needs-attention` with the reason `independence overridden`.

### Gating set
At 2.11.1 the `--json` document (schema.json) does not mark which findings gated. G_r is computed as: severity at or above `--fail-on` (default `medium`) AND confidence ≥ `--min-confidence` (default 0.5). Where that computes an empty set but the exit code was 2 (an ungrounded-halving edge case), treat every finding at or above `--fail-on` as gating and say so in the round log (D16). Then (D21) drop any candidate whose cited `file` is not in the reviewed change set (working-tree mode: paths in `git status --porcelain --untracked-files=all`; branch mode: `git diff --name-only <merge-base>...HEAD`) and list it in the round log and report as `out of change set`; such a finding cannot be resolved by editing the change and the CLI already demotes it internally. T122 replaces both rules with the CLI's own `gating` flag.

Finding identity (for new/recurring/reintroduced and for no-progress) mirrors `findingsMatch` (src/loop.js L349): same `file`, `category` and `title`; `line_start` within 5 unless either is 0, in which case both must be 0. Two gating sets are identical when every member of each matches a member of the other and the sizes are equal (`gatingSetsEqual`, L355). T122's `fingerprint` replaces this.

### Fix step
Performed inline by the calling context (D10). For every finding in G_r, exactly one of:
- **fix**: edit the code. Fixes beyond the finding's cited file are allowed (the builder is trusted in its own session); unrelated refactors are not.
- **decline**: write a justification of at least one sentence that cites code, a test, or the spec, and record it in the round log with the finding verbatim. "Works as intended" without evidence is not a justification. A declined finding enters the declined set.
Non-gating findings may be fixed opportunistically; they are never required and never counted.

Round log entry per finding: `{ round, action: "fix"|"decline", finding (verbatim), justification?, filesEdited? }`.

### Validation
Command resolution, first hit wins: `--test <cmd>`; a test command stated in the project's CLAUDE.md/AGENTS.md; `package.json` `scripts.test`; `Makefile` target `test`; `pyproject.toml`/`pytest.ini` present → `pytest`; `Cargo.toml` → `cargo test`; `go.mod` → `go test ./...`. If nothing resolves, ask the user once at the start. If the user says there is none, or no user answers (an unattended run), continue: every summary carries `validated: false` and the prose report opens with that line (D17). This is never a stop.

After every fix step: run the command. On failure, fix the failure (it counts as part of the same fix round) and re-run; after three failed attempts in one round, stop with exitReason `validation-failed` and the output tail. No review call is spent on an unvalidated tree.

### Rebuttal (D5)
If round r declined any findings, round r+1's review is invoked with focus text appended to any user focus:

> The builder declined the following findings from the previous review and asks you to refute or withdraw each. For each one, either re-raise it with the specific evidence that defeats the justification, or omit it. Declined: [for each: title; file:line; the justification verbatim].

Classification after round r+1: a declined finding that matches (finding identity) a finding in round r+1's output is `contested`; one that does not is `withdrawn`. Contested findings are blocking and are NOT re-sent in later rebuttals (one rebuttal per finding); the builder may still fix a contested finding later, which moves it to fixed. Withdrawn findings are listed in the report and never block.

### Progress accounting
For each round record: counts of G_r by severity; `new` (matches nothing in any earlier G); `recurring` (matches G_{r-1}); `reintroduced` (matches some G_k with k < r-1 and nothing in G_{r-1}); `fixed` (members of G_{r-1} with no match in G_r that were not declined); `declined`; `roundsSinceDecrease` (rounds since |G| last fell).

### Stops and checkpoints
Evaluated after each review, in this order:
1. **clean**: exit 0 and contested set empty → exitReason `clean`, verdict `approve`. Withdrawn findings are listed.
2. **converged-with-accepted**: exit 0 and contested set non-empty → exitReason `converged-with-accepted`, verdict `needs-attention`. The report lists each contested finding with the reviewer's rebuttal and the builder's justification for the human to ratify.
3. **no-progress checkpoint**: G_r, G_{r-1}, G_{r-2} pairwise identical → checkpoint.
4. **ceiling checkpoint**: F == `--max-rounds` → checkpoint.
4b. **time checkpoint** (D23): wall-clock since the block started ≥ `--max-time` → checkpoint (exitReason `checkpoint-time` if the user stops).
5. **builder-stuck**: the builder may raise a checkpoint at any fix step with a stated reason (for example, a finding that requires a design decision).
Otherwise fix and continue.

A checkpoint pauses with the trend table (below) and ONE question with three options: continue for another `--max-rounds` block, change approach (the user supplies guidance that becomes focus text and/or a scope change), or stop. The recommendation is computed, not felt: recommend **continue** only if the combined critical+high count fell within the last 5 rounds AND no finding has been `recurring` or `reintroduced` 3 or more times; otherwise recommend **stop** and name the stuck findings. If the user stops, exitReason is `checkpoint-ceiling`, `checkpoint-no-progress`, `checkpoint-time` or `builder-stuck`, verdict `needs-attention`, surviving findings verbatim. At every checkpoint and every stop the JSON summary block is also written to `<scratchpad>/arl/<run-id>/summary.json` before the question is asked (D23), so a lost session leaves the evidence on disk.

Trend table columns: round, elapsed, critical, high, medium, low, new, recurring, reintroduced, fixed, declined, out-of-change-set, rounds-since-decrease, validated.

### Branch mode git handling (D9)
After a validated fix step (D22): `git add -- <every path the round log records as edited>` then `git commit --no-gpg-sign -m "fix(review): round <r>" -m "<one line per fixed finding title>"`. Then `git status --porcelain` must be empty; if it is not, stop with exitReason `precondition` naming the stray paths (validation by-products, generated files) instead of committing them. Never `git add -A`. The pre-run HEAD is recorded as `originalHead` and printed at every stop with `git reset --hard <originalHead>` as the undo command. The base ref is only ever read. A pushed branch is warned about once, not refused. `--no-gpg-sign` mirrors `--loop` (README L505-507): these are disposable commits to squash.

### Report (D11)
Prose: surviving gating findings verbatim (title, severity, file:line, body, recommendation), then contested with both sides, then withdrawn, then the trend table. Never softened or summarised away (same discipline as the adversarial-review skill).

JSON block, last thing in the final message, fenced as `json`:
```
{ "type": "loop_summary", "mode": "arl",
  "providers": ["<reviewer id as the CLI announced it>"],
  "iterations": <F>, "reviews": <r>,
  "verdict": "approve"|"needs-attention",
  "exitReason": "clean"|"converged-with-accepted"|"checkpoint-ceiling"|"checkpoint-no-progress"|"checkpoint-time"|"builder-stuck"|"no-independent-reviewer"|"precondition"|"review-error"|"validation-failed",
  "survivingCount": <|G_r| minus contested>, "acceptedCount": <contested count>, "withdrawnCount": <n>, "outOfChangeSetCount": <n>,
  "elapsedSeconds": <n>,
  "validated": true|false, "validationCommand": "<cmd>"|null,
  "independence": "verified"|"overridden",
  "scope": "working-tree"|"branch", "base": "<ref>"|null, "originalHead": "<sha>"|null,
  "roundLog": "<scratchpad path>" }
```
Field names shared with the CLI's `loop_summary` (`providers`, `iterations`, `verdict`, `exitReason`, `survivingCount`, `acceptedCount`, `validated`) keep their CLI meaning, so an ADLC P6 `jq 'select(.type=="loop_summary")'` ingests it unchanged. `mode: "arl"` distinguishes it. Verdict is `approve` only when exitReason is `clean` AND independence is `verified` (D24). This block is skill output, not CLI stdout; `loop-events-schema.json` (T51) is not extended by T120.

### Output discipline
Findings are quoted, never paraphrased. The skill never declares a finding fixed without a validated tree and a subsequent review that no longer raises it. The skill never exits `clean` while a contested finding exists.

## Docs repositioning (binding text intent)
README "Loop mode" opening paragraph: there are two loops. `arl` (the `adversarial-review-loop` skill) is for an agent session: the session that wrote the code fixes, an independent model reviews, the human ratifies declines. `--loop` is for unattended runs (CI, a bot converging a branch) where no calling agent exists; it spawns a separate fixer CLI and is the subject of the 3.0.0 independence work. Inside an agent harness prefer `arl`.

`skills/adversarial-review/SKILL.md` L62 and L71 (D27): the `--loop` bullet opens with the redirect, before any explanation: "`--loop` — not for use inside an agent session: use the `adversarial-review-loop` (arl) skill, which fixes in this context. `--loop` is the unattended/CI mode: ...". The arl frontmatter description contains the literal `--loop` so the trigger matcher sees the term.
