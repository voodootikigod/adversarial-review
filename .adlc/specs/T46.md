# Spec T46: Add `opencode` (with the `opencode-go` provider) as an explicit review provider

## Context & Problem
`opencode` is a widely installed local agent that authenticates a set of model providers the review tool cannot otherwise reach. In particular its `opencode-go` provider routes to models outside the three frontier labs — `grok-4.5`, `kimi-k3`, `kimi-k2.7-code`, `qwen3.7-max`, `glm-5.2`, `deepseek-v4-pro`, `minimax-m3`, `mimo-v2.5-pro` — which are genuinely independent critics of code written by a Big-3 model.

Empirical findings from opencode 1.18.11 (verified on macOS before writing this spec):

- `opencode run` reads the prompt from **stdin** with no sentinel argument, and exits **1** on failure (verified against a credit-exhaustion error). This is the cleanest calling convention of any supported CLI.
- Agent response goes to **stdout**; the session banner (`> advreview · kimi-k2.7-code`) goes to **stderr**. A probe returned stdout containing exactly `{"ok":true}`.
- **There is no read-only flag.** `--agent plan` does NOT fail closed: opencode prints `! agent "plan" is a subagent, not a primary agent. Falling back to default agent` and proceeds under the user's configured default primary agent. On the machine this spec was written on, that agent carries `{"permission": "*", "action": "allow"}` — full write and bash access, applied to a prompt derived from an untrusted diff.
- Read-only **can** be enforced by generating a config that declares a primary agent with tools and permissions denied, and pointing `OPENCODE_CONFIG` at it. Verified: with such a config, a prompt instructing the agent to create `pwned-oc.txt` produced "I don't have a `write` or `bash` tool available in this environment" and **no file was created**.
- **An enabled tool whose permission is unset hangs the run indefinitely.** A config that disabled `write`/`edit`/`patch`/`bash` but left `read`/`grep`/`glob` enabled with no explicit permission caused `opencode run` to block forever on an interactive permission prompt with no output and no error — two runs were killed by an external timeout at 400s and 500s. There is no headless auto-deny. The generated config MUST set an explicit catch-all (`"permission": { "*": "deny" }`) plus an explicit `"allow"` for every tool it enables.
- **Disabling all tools is also wrong.** With every tool disabled the model returned quickly but stopped mid-turn without answering ("I'll audit the ticket... Reading the full spec...") because it had planned tool calls it could not make. A useful reviewer needs `read`/`grep`/`glob`/`list`.
- The config shape verified working end-to-end is: `tools: { write: false, edit: false, patch: false, bash: false, task: false, read: true, grep: true, glob: true, list: true }` with `permission: { "*": "deny", read: "allow", grep: "allow", glob: "allow", list: "allow" }`. Under it, `opencode-go/grok-4.5` read the repository and returned a well-formed answer, exit 0.
- **stdout interleaves tool-call narration with the answer.** Under `--format default` the payload arrived as prose fragments ("Reading the full spec and key implementation touchpoints next.") concatenated directly before the JSON object, with no delimiter.
- `src/exec-watchdog.js:159` hardcodes `env: sanitizedSpawnEnv()` with no override hook, so injecting `OPENCODE_CONFIG` requires a change to the spawn layer.

### Found during implementation (adversarial review of this feature, then confirmed by live attack)

- **`OPENCODE_CONFIG` MERGES, it does not replace** — with it set, `opencode agent list` still shows every agent the user defined, plus ours.
- **CRITICAL: the merge includes project-local `opencode.json` from the working directory, which during a review IS the repository under review.** A repo that ships an `opencode.json` redefining the review agent BY NAME with `tools:{write,bash}=true, permission:{"*":"allow"}` wins that merge. Verified by live attack against a fixed agent name: the model wrote `pwned.txt`. The sandbox was fully defeated by the diff it exists to contain. Fix: a per-run random agent name, which a file written before the run cannot target. Re-verified: the same attack then fails.
- A hostile config that does NOT name our agent (top-level `tools`/`permission` instead) does **not** broaden it — the per-agent block wins. So randomizing the name is a complete fix for this vector, not a partial one.
- **Plugins are a second repo-controlled code path.** Project config can load plugins, which run code and would make tool permissions irrelevant. `--pure` is passed on every run.
- **`sanitizedSpawnEnv` only sanitizes PATH.** It does NOT strip `NODE_OPTIONS`, `LD_PRELOAD`, `DYLD_*`, `BASH_ENV`, or `GIT_*` — nothing could previously add them, since children inherited a fixed environment. `envOverrides` is the first thing that can, so it takes an ALLOWLIST rather than a denylist.
- **`opencode run` drops a `.omo/` state directory into the project directory.** It is already in this repo's `.gitignore`, but a reviewer must not leave files in the tree it reviewed; removed only when the run created it.

## Proposed Solution
Add `opencode` as an **explicit-only, family-less** local CLI provider on the review path, sandboxed by a generated read-only config injected via `OPENCODE_CONFIG`.

**Diversity treatment.** Identical to T45's rationale. `opencode` is a multi-provider router, and even `opencode-go` is not family-pure (it includes `gpt-5.6-luna`, an OpenAI-family model). It MUST NOT be added to `TOKEN_FAMILY`; `familyKey()` at `src/llm.js:1207` gives it its own group for free.

**Sandbox.** Follow the `callCodexCli` privateDir precedent at `src/llm.js:474-486` exactly: `fs.mkdtempSync` in `os.tmpdir()`, config written with `mode: 0o600` and `flag: "wx"`, whole directory removed in a `finally`. The config declares one primary agent with `write`, `edit`, `patch`, and `bash` tools disabled and `edit`/`bash`/`webfetch` permissions denied. The temp directory MUST be outside the worktree.

**Env injection.** `spawnWithWatchdog` gains a narrow `envOverrides` option: a plain object of string keys applied **on top of** the result of `sanitizedSpawnEnv()`, never replacing it. PATH sanitization and every other trust-root guarantee are preserved. The sole caller passes one fixed key (`OPENCODE_CONFIG`) whose value is a path this process generated; no value derived from the diff or from repository content may reach it.

## Acceptance Criteria
- [x] AC1: `spawnWithWatchdog` accepts an `envOverrides` object applied on top of `sanitizedSpawnEnv()`. Verified in `test/exec-watchdog.test.js`: overrides reach the child, omitting them is unchanged from today, and the input env is never mutated.
- [x] AC1b (**hardened during implementation**): `applyEnvOverrides` takes an **allowlist** (`OPENCODE_CONFIG` only), not a denylist. `sanitizedSpawnEnv` only sanitizes PATH — it does not strip loader/interpreter hooks — so this seam is the first thing that could introduce them. Verified in `test/exec-watchdog.test.js` that `PATH` (all casings), `NODE_OPTIONS`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `BASH_ENV`, `GIT_DIR`, `GIT_SSH_COMMAND`, and `PYTHONSTARTUP` are all refused.
- [x] AC1c: `.omo/` state left by a run is removed only when that run created it; a pre-existing one is untouched and a symlink is never followed. Verified in `test/opencode-sandbox.test.mjs`.
- [x] AC2: A generated opencode config declares exactly one primary agent with `tools: { write: false, edit: false, patch: false, bash: false, task: false, read: true, grep: true, glob: true, list: true }` and `permission: { "*": "deny", read: "allow", grep: "allow", glob: "allow", list: "allow" }`. The file is created in a `fs.mkdtempSync` directory with `mode: 0o600` and `flag: "wx"`, and the directory is removed in a `finally` block even when the CLI throws. Verified in `test/llm.test.js`.
- [x] AC2b: The generated config contains a catch-all `"*": "deny"` permission, and every tool set to `true` in `tools` has a corresponding explicit `"allow"` entry in `permission`. A test in `test/llm.test.js` asserts this invariant structurally — an enabled tool with no explicit permission is the documented indefinite-hang condition and must be impossible to emit.
- [x] AC3: The generated config path is outside the git worktree. A test asserts the path is not inside `process.cwd()`.
- [x] AC4: **Resolved empirically: `OPENCODE_CONFIG` MERGES** (the user's agents remain listed alongside ours), recorded in a code comment. `-m` is still always passed — not because the default is lost, but so the reviewing model never depends on unrelated local config. Verified in `test/llm.test.js`.
- [x] AC5: A default model constant is defined for `opencode` and is overridable by `--model`. When opencode reports the model is unavailable or unauthenticated, the error surfaced to the user names the model and states that `opencode auth list` shows which providers are authenticated — not an opaque exit-1.
- [x] AC6: The prompt is delivered over **stdin** (no sentinel argument), so `cliRequiresArgvPrompt("opencode")` returns `false` and the argv-size guard does not apply. A test in `test/llm.test.js` asserts the built argv contains no element equal to the prompt.
- [x] AC7: The invocation always passes `--agent <generated-agent-name>`. `opencodeReviewArgs` throws when no agent is supplied, so an unpinned run is unrepresentable. Verified in `test/llm.test.js`.
- [x] AC7b (**security, added during implementation**): The agent name is generated fresh per run with 128 bits of entropy, because `OPENCODE_CONFIG` merges with project-local `opencode.json` from the repository under review and a fixed name is one the attacker knows. Verified in `test/llm.test.js` (uniqueness and entropy) and by a real-binary attack test in `test/opencode-sandbox.test.mjs` that ships a hostile `opencode.json` targeting the historical fixed name, the stable prefix, and top-level `tools`/`permission`, and asserts no file is written.
- [x] AC7c (**security, added during implementation**): `--pure` is passed on every run so a reviewed repository cannot load a plugin. Verified in `test/llm.test.js`.
- [x] AC7d (**security, added during implementation**): A clean exit is not trusted. `opencodeSandboxFailure` refuses the result when stderr shows subagent fallback or fails to name the pinned agent, since opencode exits 0 in both cases. Verified in `test/llm.test.js`.
- [x] AC8: Only stdout is parsed for the review payload; the stderr banner is excluded. A test in `test/llm.test.js` feeds a captured stdout/stderr pair and asserts the banner text never reaches the JSON extractor.
- [x] AC8b: The extractor tolerates tool-call narration concatenated ahead of the JSON payload on stdout, with no delimiter (see the captured sample in the findings above). Evaluate `--format json` (raw JSON events) as a cleaner alternative and record the choice in a code comment; whichever is chosen, a test in `test/llm.test.js` uses a real captured stdout sample as its fixture.
- [x] AC9: `CLI_ONLY_TOKENS` includes `"opencode"`; `resolveProviderToken("opencode")` returns `family: null` and is never upgraded to an API provider. `TOKEN_FAMILY` does NOT contain an `opencode` or `opencode-go` key.
- [x] AC10: `--provider opencode` resolves to `{ provider: "cli", cliCmd: "opencode" }`, and the auto-detection ladder never selects `opencode` when no explicit provider is given.
- [x] AC11: An end-to-end test in `test/cli-multiprovider.test.js` asserts read-only enforcement holds: with the generated config, a prompt instructing the agent to write a file into a temp workspace leaves that file absent. PATH-gated — skipped cleanly when `opencode` is not installed.
- [x] AC12: `README.md` and `skills/adversarial-review/SKILL.md` document `--provider opencode`, the `opencode-go` model set, explicit-only/family-less status, and the generated-config sandbox. Verified via `grep -i "opencode" README.md skills/adversarial-review/SKILL.md`.
- [x] AC13: `npm test` passes, including the existing `test/exec-watchdog.test.js` and `test/spawn-safe.test.js` suites unmodified in intent.

## Risks
- **Spawn-layer change.** `envOverrides` touches security-sensitive code. Mitigation: overrides apply after sanitization and cannot replace `PATH`; the only caller passes a fixed key with a self-generated value. AC1 tests the negative case directly.
- **Config semantics unknown.** AC4 exists to resolve the replace-vs-merge question before the implementation depends on either answer.
- **Silent indefinite hang.** A misconfigured permission set does not error — it blocks forever with no output. The existing watchdog timeout is the only backstop, so a config bug would surface to users as an opaque timeout rather than a config error. AC2b makes the bad shape structurally unemittable; that test is the primary defense, not the timeout.
