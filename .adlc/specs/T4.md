# T4 — Sanitize schema before writing to disk for the local codex-CLI `--output-schema` path

## Problem

`callCodexCli` (src/llm.js:137-147) writes the raw, unsanitized JSON Schema to
disk for `codex exec --output-schema <file>`. Codex forwards that schema
verbatim to OpenAI's strict `json_schema` structured-output mode, which
requires every key in `properties` to also appear in `required`. `schema.json`'s
`findings.items` has `corroborated_by` in `properties` but not in `required`
(it is a merge-time-only annotation, never produced by a provider — see T2/T3).
OpenAI rejects the request with HTTP 400 `invalid_json_schema`, so any review
run through the local codex CLI with a schema present currently fails outright.

`sanitizeSchemaForProvider()` (src/schema-validate.js:89-97) exists specifically
to strip this class of problem and is already imported into src/llm.js and
already called at the three direct-API fetch sites in `llmCall()` — Anthropic
(src/llm.js:729), OpenAI (src/llm.js:668), Gemini (src/llm.js:626) — but never
at the local-CLI subprocess path.

## Fix

In `callCodexCli`, change the schema write (src/llm.js:147) from:

```js
if (schemaFile) fs.writeFileSync(schemaFile, JSON.stringify(schema), { mode: 0o600, flag: "wx" });
```

to:

```js
if (schemaFile) fs.writeFileSync(schemaFile, JSON.stringify(sanitizeSchemaForProvider(schema)), { mode: 0o600, flag: "wx" });
```

Use the same sanitize options as the existing OpenAI call site (src/llm.js:668)
— no `keepConstraints`, no `extraDrop` — because codex forwards this schema to
OpenAI's strict `json_schema` mode, the same target as that call site.
`sanitizeSchemaForProvider` is already imported at the top of src/llm.js; no
new import is needed.

## Out of scope

- `callCliLLM`'s handling of non-codex local CLIs (`claude`, `agy`, generic).
  They never pass `schema` to the provider as a structured-output contract —
  the schema only appears as descriptive text embedded in the prompt/system
  instruction string (src/review.js:200-204), which is not subject to OpenAI's
  strict-mode `required` rule.
- Changing `schema.json` itself. `corroborated_by` being absent from `required`
  is intentional (T2/T3): it is a merge-time-only field never produced by a
  provider. The correct fix is stripping it from the provider-facing schema,
  not adding it to `required`.
- The three existing API call sites' sanitize options.

## Acceptance criteria

- **AC1 (fix applied)** — `callCodexCli`'s `fs.writeFileSync(schemaFile, ...)`
  call wraps `schema` in `sanitizeSchemaForProvider(schema)`.
  Verification: `grep -n "writeFileSync(schemaFile" src/llm.js` shows the
  sanitize call; `git diff` shows only this one line changed in `callCodexCli`
  (plus the new test in AC2) — the three existing API call sites are untouched.

- **AC2 (regression test, real defect)** — A new test in test/llm.test.js,
  following the existing "codex CLI path uses exec --output-last-message and
  delivers full prompt via stdin" test's mock-binary pattern
  (test/llm.test.js:276-350) for PATH setup and cleanup, but the mock binary
  itself MUST be a `#!/usr/bin/env node` script (chmod 0o755), not a POSIX
  `#!/bin/sh` script — the check requires real JSON structural comparison
  (every key in `.properties.findings.items.properties` present in
  `.properties.findings.items.required`), and a shell `grep`/string-match
  substitute is a hollow check that can stay green even if sanitization is
  subtly wrong (P1 parallax resolution R1). The mock parses the
  `--output-schema <file>` argument, `JSON.parse`s that file, and
  `process.exit(1)` with a `FAIL:` stderr message if the key-inclusion check
  fails. The test calls
  `llmCall({ provider: "cli", cliCmd: "codex", timeoutMs: 10000 }, prompt, systemInstruction, schema)`
  with `schema` loaded via `JSON.parse(fs.readFileSync("schema.json", "utf8"))`
  — the real repo schema, which has `corroborated_by` optional — so the test
  exercises the actual defect rather than a synthetic one.
  Verification: `node --test test/llm.test.js` — the new test passes.

- **AC3 (mutation-proven)** — `node --test test/llm.test.js` FAILS on AC2's
  new test against pre-fix src/llm.js (`git stash` the one-line fix) and
  PASSES after re-applying it — a one-time manual check recorded in the PR
  description, not a second shipped test (P1 parallax resolution R2: only
  AC2's test ships).

- **AC4 (no regression)** — `npm test` exits 0 after the fix is applied.

## Risks / things a build agent should not do

- Do not touch the sanitize options at the three API call sites.
- Do not add `corroborated_by` to schema.json's `required` array — that would
  contradict T2/T3's design (it must remain a merge-time-only annotation).
- Do not change `callCliLLM`'s handling of non-codex CLIs.
- Do not add extra defensive validation beyond AC1/AC2 (e.g. re-running
  `validateAgainstSchema` on the sanitized schema) — out of scope per P1
  parallax resolution R3; keep the fix minimal.

## P1 interrogation resolutions (parallax + premortem)

Three independent readings of this spec converged almost completely (it is
concrete enough to leave little room for divergence) with one real
divergence: how the AC2 mock `codex` binary checks the written schema file
(shell string-matching vs. real JSON parsing). Resolved:

- **R1** — The mock binary MUST be a `#!/usr/bin/env node` script that
  `JSON.parse`s the written `--output-schema` file and does a real
  key-inclusion check, not a `sh`/`grep` string-match. A string-match mock
  would be a hollow test: it could stay green even if the sanitize call is
  wrong or missing, since `corroborated_by` still appears as raw text
  elsewhere in the schema (e.g. inside other unrelated strings).
- **R2** — AC3 ("mutation-proven") is a one-time manual verification
  performed once during implementation, not a second permanently-committed
  test. Only AC2's single test ships.
- **R3** — No additional defensive validation beyond AC1/AC2. Keep the diff
  minimal (one line in src/llm.js, one new test in test/llm.test.js).

Premortem risks incorporated into the spec/build guidance above:
- merge-forecast already flags a hard-veto scope-overlap between T1 and T4
  (both touch src/llm.js) — land and CI-verify T4 before or together with
  T1's rebase, not after, to avoid a silent conflict-resolution drop of the
  one-line fix.
- AC1's verification must confirm not just that *a* `sanitizeSchemaForProvider`
  call was added, but that it uses the OpenAI-mirroring default options (no
  `keepConstraints`, no `extraDrop`) — a build agent reaching for the
  Anthropic call site's `{ keepConstraints: true }` by analogy would still
  pass AC1's grep check (the call exists) without matching the spec's intent.
