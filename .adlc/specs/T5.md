# T5 — Consolidated `loop_summary` NDJSON event at every `--loop` terminal exit

## Problem

`--loop` (src/loop.js) emits NDJSON events only under `--json`, via
`emitEvent(jsonMode, event)` (src/loop.js:111-113): `loop_start`, `review`,
`review_result`, `stash_created`, `fix`, and `loop_end`. There is **no single
consolidated terminal record**. `loop_end` (six emission sites) carries only
`exitReason`, `iterations`, and `stashRef`; the provider list, the verdict, and
the surviving-finding count live on a *separate* `review_result` NDJSON line
emitted just before it. To build one P6 gate-manifest evidence entry —

```
adlc gate-manifest record adversarial-review \
  --evidence 'providers=<a,b>; iterations=<n>; verdict=<approve|needs-attention>; \
              exitReason=<clean|no-progress|ceiling>; surviving=<n>; accepted=<n>'
```

— a consumer must correlate two NDJSON lines by hand, per invocation. That
friction is ADR-0008's "follow-on B": it suppresses how often the loop's output
actually gets recorded as gate-manifest evidence.

## Fix

Emit ONE final `loop_summary` event — json-gated, in parity with every other
loop event — as the terminal NDJSON line at EVERY `--loop` exit. It carries
exactly the field set the `--evidence` string wants.

### 1. Pure helper (the load-bearing seam), exported for unit testing

```js
export function buildLoopSummary({ providers, iterations, exitReason, survivingCount }) {
  return {
    type: "loop_summary",
    providers,
    iterations,
    verdict: exitReason === "clean" ? "approve" : "needs-attention",
    exitReason,
    survivingCount,
    acceptedCount: 0
  };
}
```

`verdict` is **derived**, never passed in: a loop that exits without reaching a
clean review still has surviving gating findings, so any non-`clean` exit
(`no-progress`, `ceiling`, `no-diff`, `fixer-error`, `fixer-timeout`) is
`needs-attention`.

### 2. `providerLabels`, computed once at loop setup

- multi (`--providers`): `sel.providers.map((p) => p.id)`
- single: `[reviewConfig.provider === "cli" ? reviewConfig.cliCmd : reviewConfig.provider]`

### 3. Wire an emission after each `loop_end` terminal site

At each of the six terminal exits, immediately after the existing
`emitEvent(args.json, { type: "loop_end", ... })`, add
`emitEvent(args.json, buildLoopSummary({ providers: providerLabels, iterations, exitReason, survivingCount }))`
with, per site:

| site (src/loop.js) | exitReason | iterations | survivingCount |
|---|---|---|---|
| empty first review (~645) | `clean` | `0` | `0` |
| clean, gatings empty (~747) | `clean` | `fixCount` | `0` |
| no-progress (~759) | `no-progress` | `fixCount` | `gatings.length` |
| ceiling (~774) | `ceiling` | `fixCount` | `gatings.length` |
| fixer error/timeout (~891) | `fixer-error` \| `fixer-timeout` | `fixCount` | `gatings.length` |
| no-diff (~905) | `no-diff` | `fixCount` | `gatings.length` |

`gatings` is in scope at the no-diff / fixer-error sites (both are inside the
`while` loop after `gatings` is computed).

### 4. `acceptedCount` is always `0`

Per ADLC `docs/toolkit.md`, `accepted` = "findings acknowledged with **documented
justification**" — a *human* P6 decision. The automated loop cannot make it, so it
emits `0`; the field exists to make the evidence string complete and
copy-pastable, and the human overrides it when recording. Documented in the spec
and in the code comment at the helper.

### 5. Docs

Note `loop_summary` in the README loop section and `src/utils.js` `HELP_TEXT`
loop block (one line each). No new flag.

## Out of scope

- A separate `--summary` flag — `loop_summary` rides the existing `--json`
  stream (parity with all other events). The issue offers `--summary` as an
  *alternative*, not a requirement.
- A human-readable (non-json) summary line.
- Changing any existing event's shape/fields (including `loop_end`), or the
  single/multi-provider exit codes.
- Automatically computing `acceptedCount` (human-owned P6 value).

## Acceptance criteria

- **AC1 (unit — verdict derivation + shape)** — In `test/loop-summary.test.mjs`:
  `buildLoopSummary` returns `verdict === "approve"` **iff** `exitReason ===
  "clean"`, checked across all six exit reasons (`clean`, `no-progress`,
  `ceiling`, `no-diff`, `fixer-error`, `fixer-timeout`); `acceptedCount === 0`
  in every case; the returned object's keys are exactly
  `["type","providers","iterations","verdict","exitReason","survivingCount","acceptedCount"]`;
  and `providers`, `iterations`, `survivingCount` pass through byte-identical to
  the input. Verify: `node --test test/loop-summary.test.mjs`.

- **AC2 (end-to-end — clean exit)** — Driving the real `bin/cli.js` in `--loop
  --json` mode via the `runLoopCli` harness pattern
  (test/loop-providers.test.mjs) with a single reviewer mock returning `APPROVE`
  and a no-op fixer: the parsed NDJSON on stdout contains exactly one
  `loop_summary` line, it is the LAST line, and it equals
  `{ type:"loop_summary", providers:["claude"], iterations:0, verdict:"approve",
  exitReason:"clean", survivingCount:0, acceptedCount:0 }`. Verify: `node --test
  test/loop-summary.test.mjs`.

- **AC3 (end-to-end — non-clean, surviving > 0)** — verified by `node --test test/loop-summary.test.mjs`. Two runs:
  (a) `no-diff`: reviewer mock `FLAG` + no-op fixer → exit 2, and the terminal
  `loop_summary` has `verdict:"needs-attention"`, `exitReason:"no-diff"`,
  `survivingCount >= 1`;
  (b) `no-progress`: reviewer mock `FLAG` (same finding each round) + a fixer
  that changes the file → exit 2, terminal `loop_summary` has
  `verdict:"needs-attention"`, `exitReason:"no-progress"`, `survivingCount >= 1`.
  This proves the `gatings.length` wiring at a `> 0` site (not just the constant
  `0` clean path). Verify: `node --test test/loop-summary.test.mjs`.

- **AC4 (json-gated)** — A non-`--json` clean loop prints NO `loop_summary`
  token to stdout (parity with all other loop events). Verify: assert
  `!stdout.includes("loop_summary")` in the harness with `--json` omitted.

- **AC5 (no regression)** — `npm test` exits 0; existing `loop_end` assertions
  in the suite still pass (their event shape is untouched).

- **AC6 (mutation-proven, one-time manual)** — verified by re-running `node --test test/loop-summary.test.mjs` after each hand-applied mutation. With the implementation mutated
  in three independent ways, the suite fails, then passes on restore:
  (i) hard-code `verdict: "approve"` in `buildLoopSummary` → AC3 fails;
  (ii) delete the `loop_summary` emission at the clean site → AC2 fails;
  (iii) delete it at the no-diff site → AC3(a) fails.
  Recorded in the PR description / manifest, not shipped as extra tests.

## Risks / things a build agent should not do

- Do not route `loop_end` and `loop_summary` through a single refactored helper
  that rewrites the six terminal sites — that risks regressing the tested
  `loop_end` shapes (AC5). Keep the change additive: one new emission line per
  site.
- Do not gate `loop_summary` on anything other than `args.json`.
- Do not compute `acceptedCount` from findings — it is the human P6 value; emit
  `0`.
- Do not derive `verdict` from the model's self-reported `result.verdict`;
  derive it from `exitReason` (`clean` ⇒ `approve`).
- Do not add a `--summary` flag or non-json output.

## P1 interrogation resolutions (premortem + parallax, self-answered)

- **R1 (verdict source)** — Derive `verdict` from `exitReason`, not from the
  last review's `result.verdict`. Rationale: a `no-diff`/`fixer-error` exit can
  follow a review whose model verdict was self-reported inconsistently; the loop
  is terminating with unresolved gating findings, which is definitionally
  `needs-attention`. `clean` is the only approve state. This keeps the summary in
  lockstep with the exit code (0 clean / 2 otherwise).
- **R2 (`acceptedCount` semantics)** — Confirmed against `docs/toolkit.md`:
  `accepted` = human-justified acceptance, not loop-computable. Emit `0`; never
  conflate it with "findings the loop fixed" (that would be a misleading count a
  gate-manifest reader would treat as human sign-off).
- **R3 (`survivingCount` at non-clean sites)** — Use `gatings.length` (the
  terminal unresolved gating set for that round), not a union across rounds — the
  evidence field is "findings that persist after all iterations", i.e. what still
  gates at exit. `0` only on `clean`.
- **R4 (empty-first-review site)** — `iterations: 0`, `exitReason: clean`,
  `survivingCount: 0`: the working tree was empty, nothing gated, nothing ran.
- **R5 (test seam)** — `runLoop` calls `process.exit` and spawns real CLIs, so
  the suite unit-tests the exported pure helper (AC1) and drives the real binary
  via the existing `runLoopCli` harness for wiring/json-gating (AC2–AC4). This
  matches the existing loop test convention (exported pure fns + end-to-end
  binary drives), not in-process `runLoop` calls.
